# Vector Index

A vector index uses approximate nearest neighbor (ANN) search to find rows with
embeddings similar to a query vector. On a Data Evolution append table, Paimon
uses the matching row IDs to read the requested columns.

[![Build an index from the embedding column and its row IDs. Search the index shards with a query vector, then read the requested columns for the top-K row IDs.](/img/multimodal-vector-index-flow.svg)](/img/multimodal-vector-index-flow.svg)

The examples use Data Evolution append tables. For setup, coverage and refresh,
or the primary-key index lifecycle, see [Global Index](../global-index#prerequisites),
[Manage Global Indexes](./manage-indexes), and
[Primary-Key Global Index](../../primary-key-table/global-index).

## Build Vector Index

Load the embeddings before building the index. For Python builds and queries,
install `pypaimon[vindex]` or the matching `paimon-vindex==0.6.0` dependency.

### Supported Columns

| Embeddings per row | Column type | Embedding dimension |
|---|---|---|
| One | `ARRAY<FLOAT>` | Set `<index-type>.dimension` to the array length. The default is `128`. |
| One | `VECTOR<FLOAT, d>` | Paimon reads `d` from the column type. |
| List | `ARRAY<VECTOR<FLOAT, d>>` | Paimon reads `d` from the inner `VECTOR` type. |
| List | `ARRAY<ARRAY<FLOAT>>` | Set `<index-type>.dimension` to the length of each inner array. |

For instructions on declaring a `VECTOR` column, see [Vector Storage](../vector).

### Build an Index on a List of Vectors

On a Data Evolution append table, each row can hold a different number of
embeddings. Each embedding list column can have its own range-sharded `ivf-flat`,
`ivf-pq`, `ivf-sq`, `ivf-rq`, or `diskann` index. These indexes require cosine
similarity and use it by default. A range with no embeddings produces no index file.

For the SQL examples, create a Data Evolution table `db.documents` with an
`id INT` column and a `chunks ARRAY<VECTOR<FLOAT, 2>>` column. Define `chunks`
using `DataTypes.ARRAY(DataTypes.VECTOR(2, DataTypes.FLOAT()))` in Java or
`pa.list_(pa.list_(pa.float32(), 2))` in a PyArrow schema. Load the sample rows
and build the index in Spark SQL.

```sql
INSERT INTO db.documents VALUES
    (1, array(array(1.0f, 0.0f), array(0.0f, 1.0f))),
    (2, array(array(1.0f, 1.0f)));

CALL sys.create_global_index(
    table => 'db.documents',
    index_column => 'chunks',
    index_type => 'ivf-flat',
    options => 'ivf-flat.nlist=1'
);
```

If `chunks` is `ARRAY<ARRAY<FLOAT>>` with two-element embeddings, add
`ivf-flat.dimension=2` to the build options.

## Vector Search

Match the query vector dimension to the indexed embeddings. The following
examples request up to five rows from the three-dimensional `embedding` index.
`ivf.nprobe=1` probes the sample index's only cluster.

<Tabs groupId="vector-search">

<TabItem value="spark-sql" label="Spark SQL">

```sql
-- Search for top-5 nearest neighbors
SELECT id, name, __paimon_search_score
FROM vector_search('my_table', 'embedding', array(1.0f, 2.0f, 3.0f), 5)
ORDER BY __paimon_search_score DESC, id;
```

</TabItem>

<TabItem value="flink-sql-procedure" label="Flink SQL (Procedure)">

Flink's `CALL` procedure returns rows as JSON strings.

```sql
-- Search for top-5 nearest neighbors
CALL sys.vector_search(
    `table` => 'db.my_table',
    vector_column => 'embedding',
    query_vector => '1.0,2.0,3.0',
    top_k => 5
);

-- With projection (only return specific columns)
CALL sys.vector_search(
    `table` => 'db.my_table',
    vector_column => 'embedding',
    query_vector => '1.0,2.0,3.0',
    top_k => 5,
    projection => 'id,name,__paimon_search_score',
    options => 'ivf.nprobe=1',
    `where` => 'id > 100'
);
```

</TabItem>

<TabItem value="java-api" label="Java API">

```java

float[] queryVector = {1.0f, 2.0f, 3.0f};
GlobalIndexResult result = table.newVectorSearchBuilder()
        .withVector(queryVector)
        .withLimit(5)
        .withVectorColumn("embedding")

    });
}
```


rows in score order, see [Read Scored Results](./manage-indexes#read-scored-results).

### Search a List of Vectors

Spark SQL, Flink SQL, Java, and PyPaimon can search columns that store multiple
embeddings per row. The SQL examples use the
[index on `db.documents.chunks`](#build-an-index-on-a-list-of-vectors).

A single query vector ranks rows by their best matching embedding. A query matrix
uses MaxSim to rank rows. For every query vector, take the highest cosine similarity
among a row's embeddings, then sum those similarities. Each row appears at most once.
Null embeddings are skipped. A row with no embeddings has no score.
Query matrices require at least one vector, fixed inner dimensions and finite coordinates.

[![For the sample row with id 1, the query vectors [1, 0] and [0, 1] each have a best cosine match of 1 against the row's embeddings. MaxSim adds the two maxima for a row score of 2.](/img/multimodal-vector-maxsim.svg)](/img/multimodal-vector-maxsim.svg)

Spark SQL accepts a deterministic matrix expression that it can evaluate during analysis,
such as a nested array literal, in an uncorrelated `vector_search` call. A correlated
`LATERAL vector_search` call takes one query vector per outer row.

```sql
SELECT id, __paimon_search_score
FROM vector_search('db.documents', 'chunks', array(array(1.0f, 0.0f), array(0.0f, 1.0f)), 10)
ORDER BY __paimon_search_score DESC, id;
```

Row `1` scores `2`, and row `2` scores approximately `1.414`.

In Flink SQL, pass the matrix as a JSON string to the search procedure. The procedure
executes matrix queries locally even when `vector-search.distribute.enabled` is enabled.

```sql
CALL sys.vector_search(
    `table` => 'db.documents', vector_column => 'chunks',
    query_vector => '[[1,0],[0,1]]', top_k => 10,
    projection => 'id,__paimon_search_score'
);
```

For a matrix query, Paimon retrieves approximate candidates for each query vector.
When several matched embeddings share a row ID, the reader keeps the highest
score for that ID and can request more distinct candidates before applying the
post-filter. Paimon scores the union of candidate rows against their complete
embedding lists from the query snapshot.

The reader requests up to four times the final limit per query vector per shard
by default. Set `refine_factor` to change that multiplier for any of the five
indexes. Uncovered rows included by the search mode use the same MaxSim scoring.

For matrix queries, Java uses `newVectorSearchBuilder().withMultiVector(float[][])`.
PyPaimon uses `new_vector_search_builder().with_multi_vector(vectors)` with a
compatible native runtime. For independent top-K results per vector, use the
batch vector search builder.

### Filter Vector Search in Python

Use `with_filter` to restrict matches by scalar columns. This example builds a
BTree index on `category` in the shared example table.

```python
from pypaimon.common.predicate_builder import PredicateBuilder

table = catalog.get_table("db.my_table")
table.create_global_index("category", index_type="btree")

predicate = (
    PredicateBuilder(table.fields)
    .equal("category", "electronics")
)

result = (
    table.new_vector_search_builder()
    .with_vector_column("embedding")
    .with_query_vector([1.0, 2.0, 3.0])
    .with_limit(5)
    .with_filter(predicate)
    .execute_local()
)
```

Exact scalar index results restrict ANN search to matching row IDs. If the
scalar indexes cannot evaluate the predicate, each shard retrieves ANN
candidates and checks their filter columns from the pinned query snapshot.
The coordinator merges the filtered results from the shards.

`vector-index.post-filter.candidates-factor` is a positive integer with default `10`.
The candidate count is `max(original Top-K * factor, required reranking limit)`,
capped by the shard size and the backend integer limit. Top-K 10 normally requests
100 candidates. Batch execution can split large inputs into memory-bounded chunks.
On single-vector columns, each query runs ANN once per shard. Post-filtering
can return fewer than `top_k` rows, even zero, when matches fall outside the
candidates. Increasing the factor adds candidates and increases ANN and scalar
filter work.

Raw searches outside vector index coverage follow the configured index search
modes. When a scalar index can evaluate the predicate and covers only some
rows, setting `scalar-index.prefilter.search-mode` to `full` or `detail` also plans
raw scans for its uncovered rows. See [Coverage and Freshness](./manage-indexes#coverage-and-freshness).

Some scalar index answers contain unverified candidates. Examples include
`contains`, ends-with, or `LIKE` on a BTree index and conjunctions with a
condition that no index can evaluate. By default, Python excludes these
candidates and logs a warning, so the result may hold fewer than `limit` rows.
Set `global-index.filter.refine-from-data=true` to verify the candidates against
their filter columns. That read runs on the caller and can cover every candidate row.

### Python Tables with Deletion Vectors

Python can build native vector indexes on Data Evolution append tables
with deletion vectors enabled, including tables created with the multimodal API's
default options:

```python
import pyarrow as pa
import pypaimon.multimodal as pm

connection = pm.connect(options={"warehouse": "/tmp/paimon-warehouse"})
table = connection.create_table(
    "vectors",
    schema=pa.schema([("id", pa.int64()), ("embedding", pa.list_(pa.float32(), 2))]),
    options={"file.format": "parquet"},
)
table.add([{"id": 1, "embedding": [0.0, 1.0]}, {"id": 2, "embedding": [1.0, 1.0]}])
table.create_index("embedding", "ivf-flat", options={
    "ivf-flat.nlist": "1", "ivf-flat.distance.metric": "l2",
})
table.delete("id = 1")
print(table.search([0.0, 1.0]).select(["id"]).limit(1).to_list())  # [{"id": 2}]
```

Index builds preserve physical row IDs, including rows already marked as deleted.
Search applies the deletion vectors from its query snapshot before selecting
top-K results, so logical deletes do not require rebuilding the index. Logical
deletion does not physically remove vectors from existing index files.

## Choose an Index Type

| Index type | Layout | When to use it |
|---|---|---|
| `ivf-flat` | IVF with flat vector storage | Favor recall when memory and storage allow it. |
| `ivf-pq` | IVF with product quantization | Minimize IVF index size when stronger quantization is acceptable. |
| `ivf-sq` | IVF with 8-bit scalar-quantized residuals | Favor search throughput with one byte per vector dimension. |
| `ivf-rq` | IVF with rotated residual quantization | Favor recall on a compact IVF index when higher scan cost is acceptable. |
| `diskann` | DiskANN graph with persisted rerank vectors | Serve high-recall queries on immutable collections from a local SSD or a complete local cache. |

For index selection guidance, storage details, and the native API, see the
[paimon-vindex documentation](https://paimon.apache.org/docs/vector-index/).

## Build Options

Build options for native vector indexes:

| Option | Default | Description |
|---|---|---|
| `<index-type>.sharding` | `range` | Use `centroid` to train an outer router per row-ID range in a Spark or PyPaimon Data Evolution build. |
| `<index-type>.centroid.nlist` | Automatic | Number of outer centroids per contiguous row-ID range with centroid sharding. |
| `<index-type>.dimension` | `128` for `ARRAY<FLOAT>` | See [Supported Columns](#supported-columns) for how each column type supplies the dimension. |
| `<index-type>.distance.metric` | `inner_product` for single-vector columns, `cosine` for lists | Single-vector columns support `l2`, `cosine`, and `inner_product`. List columns support `cosine`. |
| `<index-type>.ivf.coarse-assignment` | `auto` | Build-time list assignment for all IVF types. `auto` uses Vamana when `dimension × nlist ≥ 1,000,000` and exact assignment otherwise; `exact` always uses exact assignment. |
| `<index-type>.ivf.train.max-points-per-centroid` | `256` | Positive coarse K-means training limit for all IVF types: at most `nlist × value` vectors. |
| `<index-type>.train.sample-ratio` | `1.0` | Ratio of vectors sampled for native index training. Must be greater than `0` and less than or equal to `1`. Lower values reduce training memory and build cost, but may reduce index quality. |
| `<index-type>.nlist` | Automatic | Number of clusters for the four IVF types. When omitted, paimon-vindex resolves it from the shard's non-null vector count. |
| `<index-type>.pq.code-ratio` | `0.0625` | Relative PQ-code budget for `ivf-pq` and `diskann`. |
| `<index-type>.pq.m` | Automatic | Expert override for the PQ sub-vector count used by `ivf-pq` and `diskann`. |
| `ivf-pq.ivf.pq-encoding` | `auto` | IVF-PQ build-time encoding. `auto` selects an accelerated backend when supported; `canonical` uses the canonical encoder. |
| `<index-type>.pq.train.max-points-per-centroid` | `256` | Positive PQ training limit for `ivf-pq` and `diskann`: at most `2^pq.bits × value` vectors per subquantizer. |
| `ivf-pq.pq.use-opq` | Automatic | Explicitly enables or disables OPQ. Without an explicit value, a `target-recall` of at least `0.9` enables it. |
| `ivf-rq.rq.bits` | `4` | Persisted IVF-RQ residual width. Supported values are `1` through `8`; changing it requires rebuilding the index. |
| `<index-type>.target-recall` | Not set | Build-policy hint used by `ivf-pq` and `diskann`. Validate the resulting recall on held-out queries. |
| `<index-type>.max-bytes-per-vector` | Not set | Storage objective and conservative preflight bound for `ivf-pq`, `ivf-rq`, and `diskann`. |

Use the index-prefixed keys in table properties, SQL procedure options, and Python
build options. For example, the following IVF-PQ build selects the non-default
exact and canonical paths and lowers both training limits from `256` to `128`:

```sql
CALL sys.create_global_index(
    table => 'db.model_embeddings',
    index_column => 'embedding',
    index_type => 'ivf-pq',
    options => 'ivf-pq.ivf.coarse-assignment=exact,ivf-pq.ivf.pq-encoding=canonical,ivf-pq.ivf.train.max-points-per-centroid=128,ivf-pq.pq.train.max-points-per-centroid=128'
);
```

Omit these options to retain the defaults in the table above. The native names
`ivf.coarse-assignment`, `ivf.pq-encoding`,
`ivf.train.max-points-per-centroid`, and `pq.train.max-points-per-centroid` are
also accepted directly; prefer index-prefixed names in table properties to avoid
sharing a setting across index types. Use `fields.<field-name>.<option>` to
override a table property for one vector column. Explicit procedure or Python
options override table properties; within either source, field-prefixed options
override index-prefixed options, which override bare native names. An
inapplicable stored table property is ignored, while an explicitly supplied
option that does not apply to the selected index type is rejected.

Additional paimon-vindex DiskANN build options:

| Option | Default | Description |
|---|---|---|
| `diskann.build-preset` | `balanced` | Coherent `fast_build`, `balanced`, or `high_recall` build policy. |
| `diskann.deployment-profile` | Not set | Deployment objective used to choose a storage layout. |
| `diskann.pq.bits` | `8` | Resident PQ-code width. Supported values are `4` and `8`. |
| `diskann.max-degree` | `64` | Maximum graph out-degree. |
| `diskann.build-search-list-size` | `max(100, max-degree)` | Candidate width during graph construction. |
| `diskann.alpha` | `1.2` | Robust-prune threshold. |
| `diskann.seed` | `42` | Reproducible initialization and build-order seed. |
| `diskann.memory-budget-bytes` | `8 GiB` | Internal graph-build memory estimate used to select normal or sharded construction. |
| `diskann.storage-layout` | `auto` | Explicit `compact` or `interleaved` layout override. |
| `diskann.raw-vector-encoding` | `auto` | Explicit `f32` or `f16` persisted rerank-vector encoding. |
| `diskann.build-distance` | `auto` | Explicit product-quantized or full-precision build traversal override. |

### Quantized and DiskANN Builds

Choose one of these builds for a populated `db.model_embeddings` table with
768-dimensional `embedding ARRAY<FLOAT>` values. Train quantized indexes on a
representative dataset large enough for the chosen clustering and quantization
parameters.

```sql
CALL sys.create_global_index(
    table => 'db.model_embeddings',
    index_column => 'embedding',
    index_type => 'ivf-pq',
    options => 'ivf-pq.dimension=768,ivf-pq.distance.metric=cosine,ivf-pq.nlist=256,ivf-pq.pq.code-ratio=0.0625'
);
```

Alternatively, build a DiskANN index:

```sql
CALL sys.create_global_index(
    table => 'db.model_embeddings',
    index_column => 'embedding',
    index_type => 'diskann',
    options => 'diskann.dimension=768,diskann.distance.metric=l2,diskann.build-preset=balanced'
);
```

Pass the same option keys to Python's `create_global_index(..., options={...})`.
Use full 768-dimensional query vectors when searching either of these indexes.

### Per-Field Options

The options above can also be set at the table level (in `TBLPROPERTIES`), where they are shared
by every vector column of the same index type. When a table has multiple vector columns, you can
scope an option to a single column with `fields.<field-name>.<option>`. The field-level form takes
precedence over the column-agnostic option for that column. Use the stored table column name exactly
as `<field-name>`. Field-level vector options do not include the index-type prefix; for example,
use `fields.image_embedding.nlist` to override the shared `ivf-pq.nlist` option for
`image_embedding`:

## Search Options

Search-time options are passed with each vector search request:

| Option | Default | Description |
|---|---|---|
| `ivf.nprobe` | Automatic | Explicit number of IVF clusters to probe. When omitted, paimon-vindex derives the width from the index, `top_k`, and filter selectivity. |
| `centroid.nprobe` | Automatic | Number of centroid shards to search per row-ID range. Paimon chooses this width when omitted. Within each selected shard, `ivf.nprobe` controls the IVF lists to search and `diskann.l_search` controls the DiskANN graph search width. |
| `ivf.max_initial_filter_expansion_factor` | Disabled | Positive integer limiting filter-driven expansion of the initial automatic IVF probe width. A factor of `1` disables initial filter expansion. Progressive retries may still probe more clusters when fewer than `top_k` filtered results are found. |
| `refine_factor` | List columns use `4` for a matrix query and `1` for a single query vector. Disabled for single-vector columns. | Retrieves `top_k * refine_factor` candidates per query vector and reranks them with the original vectors stored in the Paimon table. For single-vector columns it is most useful with compressed indexes such as `ivf-pq`, `ivf-sq`, and `ivf-rq`. |
| `ivf_pq.batch_table_reuse` | `auto` | Distance-table reuse for native batched IVF-PQ searches on single-vector columns. Accepts `auto`, `on`, or `off`. |
| `ivf_pq.batch_table_reuse.max_bytes` | 512 MiB | Positive long integer limiting the memory used by IVF-PQ batch distance-table reuse. Search falls back to direct table construction when the reusable tables exceed the budget. |
| `diskann.l_search` | Automatic | paimon-vindex DiskANN graph candidate width. The automatic value uses calibration when available, otherwise `max(100, 2 * top_k)`. |

Use the same distance metric at build time and query time. Search options can be passed per query,
so you can use a larger `ivf.nprobe` or `diskann.l_search` for higher recall queries and a smaller
value for latency-sensitive queries. Do not set both in one query.

`ivf.max_initial_filter_expansion_factor` applies only to automatic IVF search and cannot be combined
with `ivf.nprobe` or `diskann.l_search`. Lower factors reduce initial filtered-search work but may
reduce Recall@K compared with uncapped automatic search. Progressive expansion occurs only when
fewer than `top_k` valid results are returned; if the capped initial search already fills `top_k`,
probing stops.

`refine_factor` also accepts the alias `rerank_factor` and hyphenated spellings such as
`refine-factor`. The four IVF indexes also accept `ivf.refine_factor`. Setting `refine_factor=1`
still performs the raw-vector rerank for the indexed candidates. Single-vector columns skip
reranking when the option is unset.
List columns always score candidate rows against their complete embedding lists.

### Shard Search Concurrency

The `global-index.thread-num` table option caps the number of index shards Java
and Python can open and search concurrently for single and batch queries. The
setting must be a positive integer and defaults to `32`. The number of splits
also bounds concurrency. Set the option to `1` for serial shard searches.

The setting applies to paimon-vindex and Lumina indexes. Parallel searches
preserve score and row-ID tie ordering. Each shard can also use native search
and I/O threads, so account for those threads and available memory when choosing
the value. Python raw-vector fallback uses table read parallelism.
