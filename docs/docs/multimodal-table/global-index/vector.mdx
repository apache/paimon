# Vector Index

Vector Index provides approximate nearest neighbor (ANN) search for vector similarity search scenarios such as
recommendation systems, image retrieval, and RAG (Retrieval Augmented Generation) applications.

Supported vector index types:

| Index Type | Description |
|---|---|
| `ivf-flat` | IVF index with flat vector storage. |
| `ivf-pq` | IVF index with product quantization. |
| `ivf-sq` | IVF index with 8-bit scalar-quantized residuals. |
| `ivf-rq` | IVF index with rotated residual quantization. |
| `diskann` | paimon-vindex DiskANN index with graph traversal and persisted rerank vectors. |

Choose the index type based on the trade-off you want:

| Index Type | Best For |
|---|---|
| `ivf-flat` | Highest recall among IVF variants when storage and memory are acceptable. |
| `ivf-pq` | The smallest IVF files when stronger quantization loss is acceptable. |
| `ivf-sq` | High compact-index throughput with one byte per vector dimension. |
| `ivf-rq` | Higher compact-IVF recall when additional scan work is acceptable. |
| `diskann` | High-recall immutable collections served from local SSD or a complete local cache. |

See the [paimon-vindex documentation](https://paimon.apache.org/docs/vector-index/) for its index
selection guidance, storage architecture, and native API details.

:::warning Upgrading paimon-vindex indexes to 0.3.0

paimon-vindex 0.3.0 does not read the experimental `ivf-hnsw-flat` and `ivf-hnsw-sq` files written
by 0.2.x. Rebuild those indexes as `ivf-flat`, `ivf-pq`, `ivf-sq`, `ivf-rq`, or `diskann` before
removing the old runtime. Keep the source vectors or a 0.2-compatible index copy until the upgrade
is accepted.

:::

For table prerequisites, see [Global Index](../global-index#prerequisites).
For refresh, coverage modes, and shared build options, see
[Manage Global Indexes](./manage-indexes).

## Build Vector Index

Create and populate the [shared example table](../global-index#prerequisites) first.
The build and search examples below use its three-dimensional `embedding` column.
For this small dataset, use `ivf-flat` with one cluster; production workloads should
choose an index type and cluster count for their own data.

For Python, install `pypaimon[vindex]` (or its matching `paimon-vindex==0.5.0`
dependency) before building or querying native vector indexes.

For `ARRAY<FLOAT>` columns, specify the dimension with `<index-type>.dimension`.
For `VECTOR<FLOAT, n>` columns, Paimon uses the dimension from the column type.
Every query vector must have that same dimension.

### Python Tables with Deletion Vectors

Python can build the native vector indexes listed above on data-evolution tables
with deletion vectors enabled, including tables created with the multimodal API's
default options:

```python
import pyarrow as pa
import pypaimon.multimodal as pm

connection = pm.connect(options={"warehouse": "/tmp/paimon-warehouse"})
table = connection.create_table(
    "vectors",
    schema=pa.schema([("id", pa.int64()), ("embedding", pa.list_(pa.float32(), 2))]),
    options={"file.format": "parquet"},
)
table.add([{"id": 1, "embedding": [0.0, 1.0]}, {"id": 2, "embedding": [1.0, 1.0]}])
table.create_index("embedding", "ivf-flat", options={
    "ivf-flat.nlist": "1", "ivf-flat.distance.metric": "l2",
})
table.delete("id = 1")
print(table.search([0.0, 1.0]).select(["id"]).limit(1).to_list())  # [{"id": 2}]
```

Index builds preserve physical row IDs, including rows already marked as deleted.
Search applies the deletion vectors from its query snapshot before selecting
top-K results, so logical deletes do not require rebuilding the index. Logical
deletion does not physically remove vectors from existing index files.

## Vector Search

Python indexed vector searches use the `global-index.thread-num` table option,
the same as Java. It must be a positive integer and defaults to `32`. Single and
batch queries open and search at most that many index shards concurrently,
bounded by the number of splits. Set it to `1` for serial shard searches. It
applies to both paimon-vindex and Lumina indexes. Results retain the same score
and row-ID tie ordering. Each shard can also use native search and I/O threads,
so choose the thread count together with those settings and the available
memory. In Python, raw-vector fallback continues to use the table read
parallelism.

The examples search the three-dimensional IVF-flat index built above. A limit of
`5` returns at most five matches; the three-row sample table returns fewer.
`ivf.nprobe=1` matches the single cluster in this example.

<Tabs groupId="vector-search">

```sql
-- Search for top-5 nearest neighbors

FROM vector_search('my_table', 'embedding', array(1.0f, 2.0f, 3.0f), 5)
ORDER BY __paimon_search_score DESC, id;
```

You can also add a scalar filter to pre-filter rows before vector search:

```python
from pypaimon.common.predicate_builder import PredicateBuilder

table.create_global_index("category", index_type="btree")

predicate = (
    PredicateBuilder(table.fields)
    .equal("category", "electronics")
)

result = (
    table.new_vector_search_builder()
    .with_vector_column("embedding")
    .with_query_vector([1.0, 2.0, 3.0])
    .with_limit(5)
    .with_filter(predicate)
    .execute_local()
)
```

Exact scalar global-index answers pre-filter the vector search. If scalar indexes cannot
evaluate the predicate, each shard retrieves ANN candidates and checks them against the
filter columns of the same pinned snapshot. The coordinator merges the filtered results;
it does not perform a full-table scalar scan or a raw scan to fill missing matches.

`vector-index.post-filter.candidates-factor` is a positive integer, defaulting to `10`.
The candidate count is `max(original Top-K * factor, required reranking limit)`, capped by
the shard size and the backend integer limit. For example, Top-K 10 normally requests 100
candidates. Batch execution may split large inputs into memory-bounded chunks. On single-vector
columns, each query runs ANN once per shard. Post-filtering may return fewer than Top-K rows, including zero even
when matches exist outside the candidates. Increasing the factor trades more ANN/scalar
work for more candidates. Post-filtering does not retry or scan raw data to fill Top-K.
Raw work outside vector coverage still follows the configured index search modes. When a
scalar index can evaluate the predicate but covers only some rows, setting
[`scalar-index.prefilter.search-mode`](./manage-indexes#coverage-and-freshness)
to `full` or `detail` also plans raw scans for its uncovered rows.

Build a BTree index for frequently used metadata filters, such as `category`, `tenant_id`,
or `event_time`, to restrict candidate row IDs before ANN.

An index answer that is only a candidate set — `contains`, ends-with or `LIKE` on a BTree index,
or a conjunction with a member no index can evaluate — is never ranked as if it matched, because
a non-matching but closer row would take a top-k slot from a matching one. By default such
candidates are excluded and a warning is logged, so the result may hold fewer than `limit` rows;
set `global-index.filter.refine-from-data=true` to verify them by reading their filter columns
instead. That read runs on the caller and can cover every candidate row.

</TabItem>

</Tabs>

A search selects top-K row IDs; reading those rows through a regular table scan
does not imply score order. See [Read Scored Results](./manage-indexes#read-scored-results)
for SQL ordering and Java/Python score access.

### Search a List of Vectors

On a Data Evolution table, Spark SQL, Flink SQL and Java can search a column containing multiple
embeddings per row. The native `ivf-flat`, `ivf-pq`, `ivf-sq`, `ivf-rq`, and `diskann`
indexes support these columns with range sharding and cosine similarity.
Omitting the metric selects `cosine`. Index creation rejects any other metric.
The column can be `ARRAY<VECTOR<FLOAT, d>>` or `ARRAY<ARRAY<FLOAT>>`. For the latter,
specify the inner dimension when building the index. Each row can contain a different
number of vectors. You can build an independent index for each such column.

```sql
-- Spark SQL
CALL sys.create_global_index(
    table => 'db.documents', index_column => 'chunks', index_type => 'ivf-flat',
    options => 'ivf-flat.dimension=2,ivf-flat.distance.metric=cosine'
);

SELECT id, __paimon_search_score
FROM vector_search('db.documents', 'chunks', array(array(1.0f, 0.0f), array(0.0f, 1.0f)), 10)
ORDER BY __paimon_search_score DESC, id;
```

A single query vector ranks rows by their best matching embedding. A query matrix
uses MaxSim to rank rows. For every query vector, take the highest cosine similarity
among a row's embeddings, then sum those similarities. Each row can occupy one
place in the result. Null embeddings are skipped. A row with no embeddings has no score.
A range with no embeddings produces no index file.
Query matrices require at least one vector, fixed inner dimensions and finite coordinates.
Spark SQL accepts a deterministic matrix expression that it can evaluate during analysis,
such as a nested array literal, in an uncorrelated `vector_search` call. A correlated
`LATERAL vector_search` call takes one query vector per outer row.
In Flink SQL, pass the matrix as a JSON string to the search procedure. The procedure
executes matrix queries locally even when `vector-search.distribute.enabled` is enabled.

```sql
CALL sys.vector_search(
    `table` => 'db.documents', vector_column => 'chunks',
    query_vector => '[[1,0],[0,1]]', top_k => 10,
    projection => 'id,__paimon_search_score'
);
```

For a matrix query, Paimon retrieves candidate rows for each query vector and scores the
union against their complete lists from the query snapshot. Candidate retrieval is approximate.
Each indexed vector carries the row ID of its source list. When several matches share that
ID, the reader keeps their highest score and can request more distinct candidate rows
before applying the post-filter.
By default, it requests up to four times the final limit per query vector per shard.
Set `refine_factor` to select that multiplier for any of the five indexes. Uncovered rows
included by the search mode are scored with the same MaxSim formula. Java exposes matrix queries through
`newVectorSearchBuilder().withMultiVector(float[][])`. For independent top-K results
per vector, use `newBatchVectorSearchBuilder().withVectors(float[][])`.

## Search Options

Search-time options are passed with each vector search request:

| Option | Default | Description |
|---|---|---|
| `ivf.nprobe` | Automatic | Explicit number of IVF clusters to probe. When omitted, paimon-vindex derives the width from the index, `top_k`, and filter selectivity. |
| `centroid.nprobe` | Automatic | Number of centroid shards to search per row-ID range. Paimon chooses this width when omitted. Within each selected shard, `ivf.nprobe` controls the IVF lists to search and `diskann.l_search` controls the DiskANN graph search width. |
| `ivf.max_initial_filter_expansion_factor` | Disabled | Positive integer limiting filter-driven expansion of the initial automatic IVF probe width. A factor of `1` disables initial filter expansion. Progressive retries may still probe more clusters when fewer than `top_k` filtered results are found. |
| `refine_factor` | List columns use `4` for a matrix query and `1` for a single query vector. Disabled for single-vector columns. | Retrieves `top_k * refine_factor` candidates per query vector and reranks them with the original vectors stored in the Paimon table. For single-vector columns it is most useful with compressed indexes such as `ivf-pq`, `ivf-sq`, and `ivf-rq`. |
| `ivf_pq.batch_table_reuse` | `auto` | Distance-table reuse for native batched IVF-PQ searches on single-vector columns. Accepts `auto`, `on`, or `off`. |
| `ivf_pq.batch_table_reuse.max_bytes` | 512 MiB | Positive long integer limiting the memory used by IVF-PQ batch distance-table reuse. Search falls back to direct table construction when the reusable tables exceed the budget. |
| `diskann.l_search` | Automatic | paimon-vindex DiskANN graph candidate width. The automatic value uses calibration when available, otherwise `max(100, 2 * top_k)`. |

Use the same distance metric at build time and query time. Search options can be passed per query,
so you can use a larger `ivf.nprobe` or `diskann.l_search` for higher recall queries and a smaller
value for latency-sensitive queries. Do not set both in one query.

`ivf.max_initial_filter_expansion_factor` applies only to automatic IVF search and cannot be combined
with `ivf.nprobe` or `diskann.l_search`. Lower factors reduce initial filtered-search work but may
reduce Recall@K compared with uncapped automatic search. Progressive expansion occurs only when
fewer than `top_k` valid results are returned; if the capped initial search already fills `top_k`,
probing stops.

`refine_factor` also accepts the alias `rerank_factor` and hyphenated spellings such as
`refine-factor`. The four IVF indexes also accept `ivf.refine_factor`. Setting `refine_factor=1`
still performs the raw-vector rerank for the indexed candidates. Single-vector columns skip
reranking when the option is unset.
List columns always score candidate rows against their complete embedding lists.

## Build Options

Build options for native vector indexes:

| Option | Default | Description |
|---|---|---|
| `<index-type>.sharding` | `range` | Use `centroid` to train an outer router for each row-ID range when building a Spark Data Evolution index. |
| `<index-type>.centroid.nlist` | Automatic | Number of outer centroids per contiguous row-ID range with centroid sharding. |
| `<index-type>.dimension` | `128` for `ARRAY<FLOAT>` | Required for `ARRAY<ARRAY<FLOAT>>`. Columns with a fixed-size vector type supply their own dimension. |
| `<index-type>.distance.metric` | `inner_product` for single-vector columns, `cosine` for lists | Single-vector columns support `l2`, `cosine`, and `inner_product`. List columns support `cosine`. |
| `<index-type>.ivf.coarse-assignment` | `auto` | Build-time list assignment for all IVF types. `auto` uses Vamana when `dimension × nlist ≥ 1,000,000` and exact assignment otherwise; `exact` always uses exact assignment. |
| `<index-type>.ivf.train.max-points-per-centroid` | `256` | Positive coarse K-means training limit for all IVF types: at most `nlist × value` vectors. |
| `<index-type>.train.sample-ratio` | `1.0` | Ratio of vectors sampled for native index training. Must be greater than `0` and less than or equal to `1`. Lower values reduce training memory and build cost, but may reduce index quality. |
| `<index-type>.nlist` | Automatic | Number of clusters for the four IVF types. When omitted, paimon-vindex resolves it from the shard's non-null vector count. |
| `<index-type>.pq.code-ratio` | `0.0625` | Relative PQ-code budget for `ivf-pq` and `diskann`. |
| `<index-type>.pq.m` | Automatic | Expert override for the PQ sub-vector count used by `ivf-pq` and `diskann`. |
| `ivf-pq.ivf.pq-encoding` | `auto` | IVF-PQ build-time encoding. `auto` selects an accelerated backend when supported; `canonical` uses the canonical encoder. |
| `<index-type>.pq.train.max-points-per-centroid` | `256` | Positive PQ training limit for `ivf-pq` and `diskann`: at most `2^pq.bits × value` vectors per subquantizer. |
| `ivf-pq.pq.use-opq` | Automatic | Explicitly enables or disables OPQ. Without an explicit value, a `target-recall` of at least `0.9` enables it. |
| `ivf-rq.rq.bits` | `4` | Persisted IVF-RQ residual width. Supported values are `1` through `8`; changing it requires rebuilding the index. |
| `<index-type>.target-recall` | Not set | Build-policy hint used by `ivf-pq` and `diskann`. Validate the resulting recall on held-out queries. |
| `<index-type>.max-bytes-per-vector` | Not set | Storage objective and conservative preflight bound for `ivf-pq`, `ivf-rq`, and `diskann`. |

Use the index-prefixed keys in table properties, SQL procedure options, and Python
build options. For example, the following IVF-PQ build selects the non-default
exact and canonical paths and lowers both training limits from `256` to `128`:

```sql
CALL sys.create_global_index(
    table => 'db.model_embeddings',
    index_column => 'embedding',
    index_type => 'ivf-pq',
    options => 'ivf-pq.ivf.coarse-assignment=exact,ivf-pq.ivf.pq-encoding=canonical,ivf-pq.ivf.train.max-points-per-centroid=128,ivf-pq.pq.train.max-points-per-centroid=128'
);
```

Omit these options to retain the defaults in the table above. The native names
`ivf.coarse-assignment`, `ivf.pq-encoding`,
`ivf.train.max-points-per-centroid`, and `pq.train.max-points-per-centroid` are
also accepted directly; prefer index-prefixed names in table properties to avoid
sharing a setting across index types. Use `fields.<field-name>.<option>` to
override a table property for one vector column. Explicit procedure or Python
options override table properties; within either source, field-prefixed options
override index-prefixed options, which override bare native names. An
inapplicable stored table property is ignored, while an explicitly supplied
option that does not apply to the selected index type is rejected.

| `diskann.deployment-profile` | Not set | Deployment objective used to choose a storage layout. |
| `diskann.pq.bits` | `8` | Resident PQ-code width. Supported values are `4` and `8`. |
| `diskann.max-degree` | `64` | Maximum graph out-degree. |

### Quantized and DiskANN Builds

The following are alternative builds for a **separate, populated** table
`db.model_embeddings` whose `embedding ARRAY<FLOAT>` values have dimension `768`.
They do not apply to the three-dimensional sample table. Choose one alternative;

```sql

    index_column => 'embedding',
```

```sql
CALL sys.create_global_index(
```

Use full 768-dimensional query vectors when searching either of these indexes.

## Centroid-Based Sharding in Spark

Spark supports centroid-based sharding for `ivf-flat`, `ivf-pq`, `ivf-sq`, `ivf-rq`
and `diskann` on Data Evolution append tables. Set `<index-type>.sharding=centroid`
when building the index. The default is `range`. Each contiguous source row-ID range in a
partition gets one routing model and one shard file per centroid. The table must enable row tracking and
Data Evolution, have no primary key, and use `bucket=-1`.

For the 768-dimensional example table above, this call builds a cosine IVF-PQ index on one
`dt` partition. The `options` apply to this build.

```sql
CALL sys.create_global_index(
    table => 'db.model_embeddings',
    index_column => 'embedding',
    index_type => 'ivf-pq',
    partitions => 'dt="2026-11-17"',
    options => 'ivf-pq.sharding=centroid,ivf-pq.dimension=768,ivf-pq.distance.metric=cosine,ivf-pq.centroid.nlist=256'
);
```

The build records the layout in the manifest. A query reads the layout for each row-ID
range, including after a restart or a change to the build options. For raw fallback, set
the column's distance metric on the table, for example with `fields.embedding.metric`.

A centroid build pins one snapshot. Spark map tasks count non-null vectors in their input
splits. Using those counts and the configured training ratio, the driver plans
the exact row ordinals that the outer IVF-FLAT trainer would retain. Each
map task reads its own splits and shuffles selected vectors by reservoir slot.
Within each contiguous range, one task trains a router on those vectors in the original
training order. Spark broadcasts that router and shuffles the range's vectors by centroid.
Independent ranges can build concurrently within the global build parallelism budget. A range
containing only null vectors records its coverage with one empty router entry. Queries skip it.
One call atomically replaces the
selected partitions' previous routers and shards of the requested type.

Queries load each selected range's routing model, select centroids with `centroid.nprobe`,
and open their shard files. Inside each selected shard, `ivf.nprobe` controls how many
local IVF lists to search. For DiskANN, `diskann.l_search` controls the graph search.
For inner product, automatic routing searches every outer shard. A high-norm vector in a distant
shard can have the largest inner product. Set an explicit outer width to trade recall for fewer
shard reads. For cosine and L2, Paimon chooses the initial width per row-ID range. The minimum is three for a four-centroid
router, four for an eight-centroid router, and eight otherwise, capped at the number of centroids.
Paimon budgets at least one sixteenth of the shards and four candidate rows per requested result
using the average shard size. A row-ID filter scales the initial width by the inverse of its
selectivity, up to all shards. If there are fewer than top-K results, automatic routing can
probe additional shards. Set `centroid.nprobe` explicitly to use a fixed outer width.

For unfiltered L2 queries on centroid-sharded `ivf-flat` and `ivf-pq`, Paimon can choose both
widths together. With 64 outer centers, an automatic outer width of eight, and top-K from 10
through 100, it checks the four nearest shard descriptors in the manifest. If all four have 64 local lists and at
least 16 × top-K vectors each, it searches those four shards with 16 local probes each.
Other layouts use independent automatic widths. Setting either probe width explicitly, or
setting `ivf.max_initial_filter_expansion_factor`, also selects independent sizing.
Both single and batched searches open each selected shard once per probe round, including
when queries in the same batch use different widths. For older descriptors without the local
list count, the reader checks the native header and computes the candidate sets for the
possible widths during the same open. This preserves the original search results.

The trained outer centers live in the routing model file. In the manifest, each
centroid index entry uses a Paimon Core envelope in `GlobalIndexMeta.indexMeta`.
For a shard, this descriptor identifies the model and centroid and wraps the local
index writer’s metadata. The local reader receives those original bytes.

The router and its shards share one `GlobalIndexMeta.rowRange`, as with BTree. Each shard stores
`rowId - rowRange.from`. The reader translates table row-ID filters into that range and adds
the range start back to matching IDs. Gaps belonging to other partitions remain eligible for raw search in
`vector-index.search-mode=detail` or `chunk`. The default `fast` mode searches
only indexed rows.
Exact refinement of centroid index candidates uses the metric recorded at build time.
For raw fallback, set the column’s metric in the table properties so unindexed rows use the
same distance as the index. For the example above, use `fields.embedding.metric=cosine`.
You can also set `fields.embedding.dimension=768` there to reuse the dimension in later builds.
Batch queries share each selected shard across the queries routed to it.

For all four IVF types, Spark shuffles vectors by their assigned routing centroid.
Each populated shard trains an independent IVF index on the vectors it receives.
For IVF-PQ, this gives each shard its own inner centroids and PQ codebook. The outer
`<index-type>.centroid.nlist` sets the number of shard slots per contiguous range. The optional
`<index-type>.nlist` sets the number of IVF lists per shard and
defaults to automatic sizing from that shard's vector count.

For example, build with
`ivf-pq.sharding=centroid,ivf-pq.centroid.nlist=64,ivf-pq.nlist=32`.
A query with `map('centroid.nprobe','4','ivf.nprobe','8')` selects four centroids per range
and searches eight local lists in each populated shard. Both levels
support automatic probe sizing. Empty local shards have a manifest row count
of zero and queries skip them.

DiskANN uses the same outer router as IVF. Each populated centroid uses the
ordinary DiskANN trainer, writer and reader. The shard trains its PQ codebook
and builds its graph from the rows it receives. DiskANN’s seed and memory budget
apply to this local build. The outer sample and coarse centers use the same
IVF-FLAT training options as the IVF shard types. An empty shard uses an
eight-byte `PCEMPTY1` marker with manifest row count zero. Queries skip that file. Empty slots remain in the complete
generation so centroid identifiers stay stable.

For example, use `index_type => 'diskann'` and
`options => 'diskann.sharding=centroid,diskann.centroid.nlist=64'`, then query with
`map('centroid.nprobe','8','diskann.l_search','64')`. Persist
`diskann.dimension` and `diskann.metric` on the table for raw fallback.

If a concurrent write or compaction replaces indexed vectors within a source range,
the commit fails and the build must be retried. Updates to other columns and appends
outside the source ranges can proceed. When row IDs are reassigned, a whole range that moves by a constant offset can
reuse its router and shards with the updated manifest range.

This build mode and its reader currently require the Java/Spark implementation
and a matching native library with centroid model APIs. Install the vector plugin on jobs that build or search these indexes. Paimon Core recognizes
routers and shards during manifest processing without loading the vector plugin.
If you wrote indexes with pre-release centroid-specific index names, drop them with the
previous build and rebuild them using the ordinary index type and the sharding option. Older readers and Python index
builders do not support this layout; drop the centroid index before downgrading
or rebuilding it through those clients. The model file and each populated shard carry
training metadata, so measure model-loading cost and total index size alongside
recall, latency, and the number of opened files.

For quantized IVF indexes, each range or centroid shard fits its own codebooks
or bounds. Compare performance at a common recall target
using separate calibration and validation queries. To measure the effect of
quantization alone, probe every outer centroid and every local list. If it remains below the target,
increasing `centroid.nprobe` alone cannot remove quantization error. For IVF-RQ,
calibrate `rq.bits`; for DiskANN, calibrate both outer probes and local graph
search width. A shared routing model does not guarantee equal recall.

Calibrate `ivf-pq.centroid.nlist` and `ivf-pq.pq.m` together with the query probe width.
Increasing `centroid.nlist` creates more centroid files, each populated file carrying its own
local model. Increasing `pq.m` uses more encoded bytes per vector;
for the current 8-bit PQ codes, `pq.m=64` uses twice the code bytes of
`pq.m=32`. OPQ and larger training limits are also workload-dependent choices,
not recall guarantees. Record the resolved build options, total index size,
query file reads, and achieved recall when comparing configurations.

### Scalar Bitmap Filters in Centroid Shards

In Spark, pass the vector column in `index_column` and a JSON object mapping scalar column names
to index types in `extra_fields`. The supported scalar index type is `bitmap`.

```sql
CALL sys.create_global_index(
    table => 'db.model_embeddings',
    index_column => 'embedding',
    index_type => 'ivf-pq',
    options => 'ivf-pq.sharding=centroid',
    extra_fields => '{"tenant_id":"bitmap","status":"bitmap"}'
);
```

Each populated centroid gets one additional scalar index file. In `GlobalIndexMeta.indexMeta`, the
centroid metadata wraps the build schema ID and one entry per `extraFieldIds` field, in the same
order. Each entry stores the index type, section length, and original Bitmap metadata. The file
stores the Bitmap sections consecutively, so the reader derives offsets from the section lengths.

A vector search can use these Bitmaps for equality, `IN`, `IS NULL`, `IS NOT NULL`, and
conjunctions of these predicates. It applies the exact matches before ranking and skips opening
the ANN file when no visible vector matches. Other predicates use the existing scalar-filter path.

To change the scalar columns, run the centroid build again with the new `extra_fields`. For the selected
partitions, the build replaces the indexes of the same type on the vector column. Pass just the
vector column as `index_column` to `sys.drop_global_index` to remove the group. Updates to any
indexed column follow `THROW_ERROR` or `DROP_PARTITION_INDEX`. Drop the group before using an
older Java reader that lacks support for centroid Bitmap files.

## Per-Field Options

The options above can also be set at the table level (in `TBLPROPERTIES`), where they are shared
by every vector column of the same index type. When a table has multiple vector columns, you can
scope an option to a single column with `fields.<field-name>.<option>`. The field-level form takes
precedence over the column-agnostic option for that column. Use the stored table column name exactly
as `<field-name>`. Field-level vector options do not include the index-type prefix; for example,
use `fields.image_embedding.nlist` to override the shared `ivf-pq.nlist` option for
`image_embedding`:

<Tabs groupId="vector-per-field-options">

<TabItem value="sql" label="Spark SQL">

```sql
CREATE TABLE multi_embedding_table (
    id INT,
    title_embedding ARRAY<FLOAT>,
    image_embedding ARRAY<FLOAT>
) TBLPROPERTIES (
    'row-tracking.enabled' = 'true',
    'data-evolution.enabled' = 'true',
    'global-index.enabled' = 'true',
    -- per-column dimensions
    'fields.title_embedding.dimension' = '768',
    'fields.image_embedding.dimension' = '512',
    -- shared by every ivf-pq column, overridden only for 'image_embedding'
    'ivf-pq.nlist' = '256',
    'fields.image_embedding.nlist' = '512',
    -- per-column training sample ratio
    'fields.image_embedding.train.sample-ratio' = '0.5'
);
```

</TabItem>

<TabItem value="python-sdk" label="Python SDK">

```python
import pyarrow as pa

from pypaimon import Schema

schema = Schema.from_pyarrow_schema(
    pa.schema([
        pa.field("id", pa.int32()),
        pa.field("title_embedding", pa.list_(pa.float32())),
        pa.field("image_embedding", pa.list_(pa.float32())),
    ]),
    options={
        "row-tracking.enabled": "true",
        "data-evolution.enabled": "true",
        "global-index.enabled": "true",
        "fields.title_embedding.dimension": "768",
        "fields.image_embedding.dimension": "512",
        "ivf-pq.nlist": "256",
        "fields.image_embedding.nlist": "512",
        "fields.image_embedding.train.sample-ratio": "0.5",
    },
)

catalog.create_table("db.multi_embedding_table", schema, ignore_if_exists=False)
```

</TabItem>

</Tabs>

These properties configure subsequent IVF-PQ builds; creating the table does not
build an index. After loading data, a build on `title_embedding` uses `nlist=256`,
while one on `image_embedding` uses `nlist=512` and trains with half of its non-null vectors.
