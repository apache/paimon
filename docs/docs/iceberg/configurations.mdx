# Configuration Reference

Set these options on the **Paimon table** to control Iceberg metadata publication. Reader-side
Iceberg catalog properties are configured separately.

## Find the Right Options

| Task | Options and guide |
| --- | --- |
| Enable publication and choose its location | `metadata.iceberg.storage`, `metadata.iceberg.storage-location`; [catalogs and metadata layout](./catalogs.md) |
| Register in Hive | `metadata.iceberg.uri`, `metadata.iceberg.hive-*`, `metadata.iceberg.database`, `metadata.iceberg.table`; [Hive Catalog](./hive-catalog.md) |
| Register in REST | `metadata.iceberg.rest.*`; [REST Catalog](./rest-catalog.mdx) |
| Publish deletion vectors | `metadata.iceberg.format-version` plus `deletion-vectors.*`; [primary key tables](./primary-key-table.mdx#deletion-vector-support) |
| Adjust manifest compatibility | `metadata.iceberg.manifest-compression`, `metadata.iceberg.manifest-legacy-version`; [query engines](./ecosystem.mdx) |
| Control metadata cleanup | `metadata.iceberg.delete-after-commit.enabled`, `metadata.iceberg.previous-versions-max` |
| Recover missing metadata versions | `metadata.iceberg.missing-base-strategy`, `metadata.iceberg.replay.*`; [replaying missing metadata](#replaying-missing-metadata) |

Metadata retention options control generated metadata files, not Paimon data-file retention.
Use Paimon's [snapshot management](../maintenance/manage-snapshots.mdx) and
[tag management](../maintenance/manage-tags.mdx) for table history.

## Replaying Missing Metadata

Paimon builds the Iceberg metadata of a snapshot on top of the metadata of the snapshot before it.
When that metadata file is missing, for example because publication was off for a while,
`metadata.iceberg.missing-base-strategy = rebuild` (the default) rebuilds the metadata from every
data file of the table. A rebuild keeps all of those files in memory, so it can run out of memory on
a large table.

With `metadata.iceberg.missing-base-strategy = replay`, Paimon instead looks for the newest older
metadata version that was built from the matching Paimon snapshot, and replays the snapshots after
it one by one from their delta manifests.

- Replay applies to tables without primary keys, deletion vectors and Data Evolution, with Iceberg
  format version 2 and the `table-location`, `hive-catalog` or `hadoop-catalog` storage. Every
  other table keeps the rebuild.
- Replay copies the manifest lists and manifests of the retained Iceberg history, so the result
  does not depend on files that another cleanup may delete. It decodes every copy and checks it
  against its manifest list, and a base with a damaged manifest is not used. Until retention drops
  the copies, they add to the size of the metadata. The original lists of the snapshots that stay
  are left in place, because readers of older metadata may still use them. Each of those snapshots
  records its originals, and they are deleted when retention drops it or when a rebuild cleans up
  the older versions.
- When replay cannot be used, Paimon rebuilds. That happens when no valid base is within
  `metadata.iceberg.replay.max-snapshots`, when one of the `metadata.iceberg.replay.*` limits is
  exceeded, when a file of the base is missing, or when the replayed row count differs from
  Paimon's. A snapshot that is no longer the latest one is not rebuilt after a failed replay.
- The limits bound the amount of work. They do not bound the heap that a step uses or how long
  one step takes.
- Replay writes the metadata file, the version hint and the external catalog entry while it holds
  the lock of the table that commits take, after it checked that its snapshot is still the one it
  started from. A rollback of a table with Iceberg metadata takes the same lock, so it cannot run
  in between. This needs a lock that the catalog provides: a table without one is not protected,
  and neither is a rollback that the catalog performs itself.

## Prefixed Properties

`metadata.iceberg.rest.<key>` passes `<key>` to the REST catalog client. It is a property prefix,
so the individual service-specific keys are not listed in the generated table above.

`metadata.iceberg.table-properties.<key>` supplies custom table properties during REST publication.
Iceberg-reserved properties are ignored. Use the dedicated Paimon options for format version
and publication behavior.
