# Multimodal Tables

Create and modify tables through `pypaimon.multimodal`. Work through Connect, Create, and Add in order to obtain the `conn` and `docs` objects used below. The creation tabs are alternatives; later examples state when a different schema is needed.

A multimodal connection wraps a Paimon catalog and a default database. Its table
API manages scalar, text, vector, and BLOB data on data-evolution tables without
primary keys. Each `add`, `overwrite`, `update`, or `delete` call handles its own
commit; use the [Python API](./python-api) for explicit writer and commit control.

Creating a multimodal table enables `row-tracking.enabled`,
`data-evolution.enabled`, `deletion-vectors.enabled`, and
`blob-as-descriptor` by default. Global index scans use full fallback coverage
through `global-index.search-mode` set to `FULL`. Data files use Paimon's
default Parquet format, and vector columns are stored in dedicated Parquet
files through `vector.file.format` set to `parquet`. These defaults require no
file-format extra:

```shell
pip install pypaimon
```

Vortex remains available as an optional format when explicitly configured.


## Connect

`connect` creates a multimodal connection from Paimon catalog options. The
`options` argument is forwarded to `CatalogFactory.create`.

<Tabs groupId="pypaimon-multimodal-connect">

<TabItem value="filesystem" label="Filesystem catalog" default>

```python
import pypaimon.multimodal as pm

conn = pm.connect(
    database="default",
    options={
        "warehouse": "file:///tmp/warehouse",
    },
)
```

</TabItem>

<TabItem value="rest" label="REST catalog">

```python
import pypaimon.multimodal as pm

conn = pm.connect(
    database="default",
    options={
        "metastore": "rest",
        "uri": "http://localhost:8080",
        "warehouse": "catalog_name",
        # Optional authentication and storage options go here.
        # "token.provider": "...",
    },
)
```

REST catalog options use the same keys as the lower-level PyPaimon catalog API.
See [REST](../concepts/rest/) for server-side catalog configuration.

</TabItem>

</Tabs>

Table names without a database are resolved against the connection's default
database. Fully-qualified names such as `"analytics.docs"` are also accepted.
Use `get_table` to open an existing multimodal table. The table must be a
data-evolution table without primary keys.

```python
docs = conn.get_table("docs")
```

## Create

<Tabs groupId="pypaimon-multimodal-create-table">

```python
import pyarrow as pa

docs = conn.create_table(
    "docs",
    schema=pa.schema([
        pa.field("id", pa.int64()),
        pa.field("content", pa.string()),
        pa.field("embedding", pa.list_(pa.float32(), 3)),
        pa.field("image", pa.large_binary()),
        pa.field("category", pa.string()),
    ]),
    ignore_if_exists=True,
)
```

</TabItem>

```python
docs = conn.create_table(
```

```python
import pyarrow as pa

docs = conn.create_table(
    "docs_by_day",
    schema=pa.schema([
        pa.field("id", pa.int64()),
        pa.field("content", pa.string()),
        pa.field("embedding", pa.list_(pa.float32(), 3)),
```

Partition keys can be specified with `partitioned`, and table options can be
specified with `options`. The multimodal API accepts `pyarrow.Schema` objects;
it does not accept field dictionaries or `pypaimon.Schema`. Use Arrow fixed-size
list types for vector columns, and Arrow binary or large-binary types for blob
columns. When creating from data, pass an explicit schema if you need exact
vector or blob types.

## Add

`add` accepts `pyarrow.Table`, `pyarrow.RecordBatch`, a list of dictionaries, a
dictionary of arrays, or a pandas DataFrame. Input columns are aligned and cast
to the Paimon table schema before writing. For a BLOB column, list, dictionary,
and pandas inputs may also contain `Blob` or `BlobDescriptor` objects. A
descriptor-backed `Blob` is copied through its stream; it is not first loaded
into Python memory.

```python
docs.add([
    {
        "id": 2,
        "content": "Paimon stores mutable lakehouse tables.",
        "embedding": [0.4, 0.5, 0.6],
        "category": "lake",
    }
])
```

## Overwrite

`overwrite` accepts the same input formats as `add` and replaces existing data
using Paimon's batch overwrite semantics. On an unpartitioned table it replaces
the whole table. On a partitioned table it follows the table's
`dynamic-partition-overwrite` option; with the default dynamic mode, only
partitions present in the input data are replaced.

```python
docs.overwrite([
    {
        "id": 3,
        "content": "Fresh replacement text",
        "embedding": [0.7, 0.8, 0.9],
        "category": "docs",
    }
])
```

The static overwrite example below uses a separate partitioned table and disables
dynamic partition overwrite when creating it. Pass the partition to replace:

```python
docs_by_day = conn.create_table(
    "docs_static_overwrite",
    schema=pa.schema([
        ("id", pa.int64()),
        ("content", pa.string()),
        ("category", pa.string()),
        ("dt", pa.string()),
    ]),
    partitioned=["dt"],
    options={"dynamic-partition-overwrite": "false"},
)
docs_by_day.overwrite(
    [
        {
            "id": 4,
            "content": "Only this day is replaced.",
            "category": "docs",
            "dt": "2024-01-01",
        }
    ],
    partition={"dt": "2024-01-01"},
)
```

## Update

`update` modifies rows matched by a SQL-like predicate.

```python
docs.update(
    where="id = 2",
    values={"category": "docs"},
)
```

On a frame table, updating ordinary columns leaves the configured
`video-frame-field` untouched. Replacing that field requires the specialized
`replace_video()` API described in [Video Frame Storage](./video#update-frame-rows-and-replace-a-video).

## Column Enrichment

Use `pypaimon.multimodal` to backfill labels or features on a Data Evolution
append table without managing row IDs and commit messages. These tables have no
primary key, use `bucket=-1`, and enable both row tracking and data evolution.
The multimodal connection sets these options when creating a table.

```python
import pyarrow as pa
import pyarrow.compute as pc
import pypaimon.multimodal as pmm

connection = pmm.connect(options={"warehouse": "/tmp/column-enrichment"})
frames = connection.create_table(
    "frames",
    schema=pa.schema([("sample_id", pa.int64()), ("image", pa.large_binary())]),
    data=[{"sample_id": 1, "image": b"first"},
          {"sample_id": 2, "image": b"second"}],
)

# Import external labels. The nullable label column is created automatically.
result = frames.merge_columns(
    pa.table({"sample_id": [2], "label": ["pedestrian"]}), on="sample_id")
print(result.added_columns)  # ('label',); the first row's label remains NULL

# Derive a new column. Only image is passed to the function; row IDs are internal.
def image_sizes(batch):
    return pa.table({"image_size": pc.binary_length(batch["image"]).cast(pa.int64())})

result = frames.add_columns(
    schema=pa.schema([("image_size", pa.int64())]),
    inputs=["image"], fn=image_sizes, batch_size=128)
print(result.updated_rows)  # 2

# A schema-only addition does not backfill values or create a data snapshot.
frames.add_columns(pa.schema([("caption", pa.string())]))
```

For embeddings, declare a fixed-size list such as
`pa.list_(pa.float32(), 768)` and return arrays of that type. The function returns
an Arrow Table or RecordBatch containing exactly the declared output columns,
with the same row count and order as its input. Inputs are RecordBatches of at
most `batch_size` rows. Functions should be deterministic and side-effect-free.
Ordinary BLOB inputs are bytes; video-frame inputs retain their descriptor
semantics and need decoding in the function. With no `fn`, omit `inputs`.
New columns must be nullable; existing column names are rejected by `add_columns`.

`merge_columns` accepts the same key forms as `merge`: a name, a list of names,
or a mapping from target names to source names. It updates only non-key columns
present in the source and never inserts rows. Omitted columns keep their values;
explicit NULL values clear nullable columns. New columns are nullable and use the
source's Arrow types; existing output types must match the table types. Matching
and key type conversion follow ordinary `merge` semantics: unmatched source rows
are ignored, NULL keys do not match, and one source row can update multiple target
rows with the same key. Multiple source rows matching the same target row are
rejected by the MERGE executor. Partition and match keys cannot be updated;
use `replace_video` to replace configured video-frame columns.

`merge_columns` delegates matching and updates to the standard MERGE executor.
With a compatible `pypaimon_rust` runtime and `write.native.enabled=true`,
supported tables use native MERGE without a separate Python target-key scan.
`add_columns` can use the native shard reader and writer with the same option;
the supplied `fn` still runs in Python. Unsupported native routes select Python
before execution.

Both methods retain files for untouched columns. Computing an image embedding
still reads the image, but does not rewrite it. Normal partial updates write the
selected columns over affected file row-ID ranges; they are not single-cell
physical writes. `add_columns` buffers outputs per original file group so a
small function batch does not repeatedly rewrite the same group.

These are local, single-writer operations on a current full-table view.
As with other table methods, reopen the table after external schema changes.
Time-travel and incremental table views are rejected. `merge_columns` materializes
the source as an Arrow table; target matching is handled by the selected MERGE
executor. The read snapshot is fixed for the
operation. Coordinate writers for the entire call.
The APIs do not provide automatic retries, checkpoints, or distributed jobs.

Successful calls return `ColumnUpdateResult` with added column names,
the source and final data snapshot IDs, and the schema ID. `updated_rows` is the
backfilled row count for `add_columns` (zero for schema-only additions) and `None`
for `merge_columns`, because MERGE does not return logical row counts. Schema-only changes
leave the data snapshot ID unchanged. Schema publication and data publication
are separate operations. Failures during schema publication or data preparation
and commit raise
`ColumnUpdateError`, retaining the original exception as `__cause__` and exposing:

| Attribute | Meaning |
| --- | --- |
| `phase` | The stage that failed: schema, compute, write, commit, result, or close |
| `schema_changed` | `True` if schema publication succeeded, `False` if it did not start, or `None` if its outcome is unknown |
| `schema_id` | The last known schema ID |
| `source_snapshot_id` | The snapshot used to match or compute rows |
| `commit_outcome` | `not_started`, `unknown`, or `committed` |

Input validation errors remain ordinary exceptions. Failed
computation can leave new columns visible as NULL, without publishing any data
updates. Prepared files are retained on failure; ordinary orphan-file maintenance
can remove abandoned files. If publication has an unknown outcome, inspect the
table before deciding whether to retry. Do not automatically retry the function
or delete prepared files after a commit error.

## Delete

`delete` removes rows matched by a SQL-like predicate. It uses the same
predicate syntax as `scan().where(...)` and `update(...)`. Multimodal tables
enable deletion vectors by default; on partitioned tables, a predicate that
references only partition columns uses the partition drop path.

```python
docs.delete(where="id = 2")
```

## Merge

Use `merge` for idempotent ingestion and matched-row deletes. The builder
delegates to Paimon's local `MERGE INTO` implementation.

`execute` takes the source rows for the merge. It accepts the same input formats
as `add`, including `pyarrow.Table`, `pyarrow.RecordBatch`, a list of
dictionaries, a dictionary of arrays, or a pandas DataFrame. A list of
dictionaries is convenient for small batches. `when_matched_update()` updates
the columns present in the source data and leaves omitted target columns
unchanged. `when_matched_delete()` deletes matched rows.
`when_not_matched_insert()` inserts the columns present in the source data and
fills omitted target columns with null.

```python
from pypaimon.multimodal import source_col

docs.merge("id") \
    .when_matched_update(
        where="source.category != target.category",
    ) \
    .when_not_matched_insert() \
    .execute([
        {
            "id": 2,
            "content": "Updated text",
            "embedding": [0.7, 0.8, 0.9],
            "category": "docs",
        }
    ])
```

Use `when_matched_delete()` for matched rows that should be removed:

```python
docs.merge("id") \
    .when_matched_delete(where="source.deleted = TRUE") \
    .when_matched_update() \
    .execute([
        {
            "id": 2,
            "content": "Updated text",
            "embedding": [0.7, 0.8, 0.9],
            "category": "docs",
            "deleted": True,
        }
    ])
```

Clause predicates use `where` for update and delete clauses. Refer to source
rows with `source.<column>` and target rows with `target.<column>`. Merge clause
predicates require Python 3.10 or newer and
`pip install 'pypaimon[datafusion]'`.

When source and target key names differ, pass a mapping from target column to
source column:

```python
docs.merge({"id": "doc_id"}) \
    .when_matched_update({"category": source_col("new_category")}) \
    .when_not_matched_insert({
        "id": source_col("doc_id"),
        "content": source_col("content"),
        "category": source_col("new_category"),
    }) \
    .execute([
        {"doc_id": 3, "content": "New doc", "new_category": "search"},
    ])
```
